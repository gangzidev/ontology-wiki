# 当前架构评审与规模化优化建议

> 评审日期：2026-11-23  
> 范围：当前工作区的后端模块、核心分析与 Wiki 检索实现、前端主要页面及相关设计文档。  
> 方法：静态检查源码、目录、SQL 映射和现有文档，未连接真实业务数据库或模型服务，也未进行 1000 表/大规模文档压测。本文区分已实现能力、从代码观察到的风险和建议目标。

## 结论

当前系统采用前后端分离的模块化单体，按 `admin / framework / system / core / query` 等 Maven 模块组织。对于目前的产品阶段，这个部署和代码组织方式总体合适，尤其查询链路已经形成目录、规划、校验、编译、DAO 的清楚分层；分析任务也具备数据库检查点、执行租约、取消和恢复等能力。

目前的主要架构问题不是缺少微服务，而是少数核心类仍承担多个业务职责、Wiki/分析数据模型以 `Map<String,Object>` 和大型 JSON 为主、Wiki 检索主要在限定候选集上做内存关键词打分，以及元数据扫描和分析生成没有形成真正面向大量表的分批流水线。1000 张表或持续增长的 Wiki 资产可以作为设计目标，但当前实现不能据此认为已验证规模能力。

建议保留模块化单体，以明确应用服务、领域能力、存储适配和外部模型/数据库访问边界为主线。优先把检索和扫描从“全量读入后筛选”演进到“持久化索引、分块召回、按需取证、增量更新”，再逐步拆分具体大型类。没有证据表明现在需要将这些模块部署为独立微服务。

## 当前分层与清晰度

### 后端

| 模块 | 当前职责 | 判断 |
|---|---|---|
| `ontology-admin` | Spring Boot 入口与运行配置 | 边界清楚 |
| `ontology-framework`、`ontology-common` | 安全、基础设施、通用组件 | 作为基础层合理，需避免业务规则反向沉入公共模块 |
| `ontology-system` | 用户、角色、菜单、部门等管理 | 与本体业务分离清楚 |
| `ontology-core` | Wiki、数据源扫描、分析任务、候选与草案、MCP、模型配置 | 覆盖面较广，内部已有 `analysis`、`wiki`、`llm` 子包，但 controller 和 LLM 编排类仍集中多个用例 |
| `ontology-query` | 查询 API、语义目录、计划、策略、编译、DAO、历史与评测 | 目前分层最清楚，边界文档与源码基本对应；仍依赖 core 的部分能力，独立性有限 |
| `ontology-scheduler`、`ontology-generator` | 定时任务与代码生成 | 通用脚手架能力，和本体核心链路关联较弱 |

查询主链路按 `Controller → Service → Catalog/Planning/Validation → Compiler → DAO` 组织，系统元数据库的持久化也已走 Mapper/XML。这个结构是可复用的边界范例。分析链路已有 `AnalysisJobServiceImpl`、知识加载、语义丰富化和任务存储等协作类，但控制器仍直接持有多种 Mapper/Service，并包含图谱解析、问答/模型配置等不同入口，接口层职责偏重。

### 前端

前端按功能页面和 API 文件组织，ontology 各功能已有目录划分，但 `chat/index.vue` 约 2197 行、`data-query/index.vue` 约 1344 行，页面状态、交互、数据请求和展示逻辑容易相互牵连。现阶段它们仍可维护，但新增功能会增加回归范围。适合按稳定的页面子域逐步拆成组件和页面级组合逻辑，避免仅按行数机械拆分。

## 规模问题与代码证据

### 数据库拥有约 1000 张表时

当前 `DataSourceScanner.scan` 基于 JDBC `DatabaseMetaData` 读取表列表，再逐表读取列、主键和外键，并可对指定表取样。分析入口允许用户指定最多 20 张变化表，增量分析会合并已有 `schemaSnapshot`。这为小范围增量更新提供了基础，但扫描接口和生成引擎仍以整份 schema map 为工作输入，代码中没有持久化的表级结构指纹/扫描批次目录，也没有按 25–50 张表切分后独立检查点并行处理的完整实现。

`OntologyGenerationEngine` 注释明确说明概念合并目前依赖标准化名称和术语表，尚无本地 Embedding。大量表下，跨表关系推断与同名概念消歧需要可追溯的规则、图结构和冲突工作流，不能只依赖全量上下文或名称相似度。

推荐的 1000 表工作流如下：

1. **扫描分批、快照持久化。** 适配各数据库系统目录的分页读取，抽取表、列、注释、主外键、索引等元数据；按数据源、schema、表名稳定排序，分批存储并计算结构指纹。样例数据单独按需读取并脱敏，默认不全库读取。
2. **先建元数据目录与关联图。** 表和字段建立可分页的元数据记录，外键形成边；无外键时补充低置信候选边（类型、命名、唯一性统计等），并明确标注推断来源和置信度。按 schema、领域、关联连通分量形成业务分析单元。
3. **批次化生成与有限上下文。** 每个分析批次只给模型必要的表/字段、直接关系邻居、检索到的 Wiki 证据和任务目标。硬性限制 token、表数、字段数、模型并发和超时；批次之间用确定性合并与冲突队列处理跨批语义。
4. **按影响范围增量重算。** 表结构指纹不变时复用已审核/已验证映射；结构变化只重算该表和受影响关系邻域。新版本保留来源快照、模型/提示版本和人工修改，旧版本可回溯。
5. **限制高成本查询与前端加载。** 表、字段、关系、候选采用服务端分页/搜索，详情按需加载；候选列表接口只返回摘要，配置大 JSON 不随普通列表返回。

### Wiki 资产持续增长时

当前问答在 SQL 中分别读取最多 100 条原始资料和 200 个 Wiki 页面，再由 `WikiLexicalRetriever` 在内存中按标题、业务域、描述做关键词打分，选最多 3 个页面并读取正文片段。中文主要依赖连续汉字的二元切分和停用词。它能为当前体量提供轻量检索，但规模增长后候选集可能遗漏相关正文内容；候选排序没有文档级倒排索引，且在 SQL 返回上限内存打分，相关证据是否进入候选集受查询实现与数据顺序影响。

`WikiIndexService` 每次刷新从 Mapper 读取最多 500 个活动页面元数据，拼成一个系统索引 Markdown 页面。这个页面可帮助模型导航，但有 500 页上限并且单页索引随资产增长而变大，不适合作为长期高召回的检索索引。

建议演进为分层混合检索：

- **摄取阶段建立可重建索引。** 原始资产和 Wiki 页面切成有重叠的语义块，持久化 `space_id / asset_id / version / chunk_no / title / section / content / source / checksum` 等字段。文档更新仅重建该资产块和索引，不全局刷新 Markdown 索引页。
- **先过滤，再召回。** 先根据用户授权、空间/资产/任务范围、状态和版本做强制过滤，然后并行执行倒排关键词/BM25 和语义向量召回。初期可以 MySQL 全文/关系型倒排或独立检索适配器，Embedding/向量库作为可替换后端，不把数据库供应商绑入领域服务。
- **融合、去重和重排。** 用可解释的加权融合或 RRF 合并词法和向量结果，按资产去重，并可选小规模 reranker。标题、字段名、业务术语、规则正文采用不同权重；每个结果保留召回分数与匹配片段。
- **按需读取证据。** 只从 Top-K 块取内容并控制 token 预算；上下文尽可能保留标题、章节、原文定位和版本。回答必须携带资产/块级引用，证据不足时明确要求澄清或回答证据不足。
- **支持知识治理。** 页面变更、删除、停用和权限变化需更新索引；记录索引版本、切分策略和模型版本，能够重建。已确认知识与原始资料需区分优先级，冲突时列出来源和更新时间，不静默覆盖。

不要一次性把所有 Wiki 正文、所有表结构或整张全局索引放进提示词。检索的准确性要通过包含中文同义词、简称、字段名、冲突规则、跨页面证据和权限边界的基准集验证，并持续监测 Recall@K、MRR/nDCG、引用正确率、无证据拒答率和端到端延迟。

## 分析范围与模型配置的页面/后端一致性

### 分析范围当前实现

| 页面能力 | 实际行为 | 状态 |
|---|---|---|
| 分析任务绑定数据源 | `AnalysisJobServiceImpl.requireTask` 校验数据源存在，分析通过其连接读取结构 | 已实现 |
| 绑定行业知识空间 | 分析只加载所选空间启用资产和规则；最多读取 100 条文档与 100 条规则，每份内容截到 12000 字符 | 已实现，但采用“最近更新优先”的硬上限；没有按当前任务主题先检索最相关文档 |
| 填写“分析范围”文本 | 普通文本会成为模型背景提示；它本身不会筛选数据库表、Schema 或字段 | 部分实现。页面字段名称容易让人理解成数据范围过滤 |
| 在范围中粘贴 SQL 样例 | 后端仅用正则从最多 20 行 SQL 中提取操作类型和表名等候选信息，不执行 SQL；其余 SQL 文本不作为业务描述发送 | 有限支持。SQL 语法解析、别名/CTE/复杂方言处理没有实现 |
| 指定变化表 | 已有草案时可选增量模式，并手工输入最多 20 个表名；这些表会重新读取，然后与旧快照合并 | 已实现的窄范围入口。全量分析仍扫描整个数据源可见的 TABLE/VIEW，任务没有独立的表白名单/排除列表 |
| 取样数据 | 数据源管理的扫描预览可选表与样例数，样例只遮蔽部分敏感字段名；分析任务页面没有选择样例表或样例数的入口，分析请求也没有传样例参数 | 页面能力与分析链路未打通。默认全量分析只取结构，不取样；直接调用接口传入变化表时也仅在非增量条件下为指定表取样 |
| 选择分析阶段 | 页面没有阶段选择控件。后端虽解析 `stages` 参数，但 `OntologyGenerationEngine.generate` 仍无条件计算阶段 1–8，只把请求阶段写进返回的 `stages` 字段 | 参数看似支持、实际未实现阶段跳过 |

因此，当前“分析范围”可靠控制的是**知识空间边界和分析任务文本背景**，以及重新分析时的**最多 20 张变化表**。它还不能在首次全量分析时让用户圈定业务表范围，也不能靠自由文本保证只分析某些表。对于表数较多的数据源，这是一个会影响扫描成本和候选精度的产品/实现缺口。建议把页面概念明确拆成“业务目标说明”和“数据库对象范围”，并实现 schema/table 多选、排除系统表、搜索分页、依赖关系预览与保存快照；增量变更则从这份范围内选择，并明确删除表与权限不可见表的处理策略。

分析知识加载也应从“按更新时间取前 100 条”改为先按空间授权过滤，再依照任务描述、数据库表/字段注释和术语做检索，最后按 token 预算取证据。提示词需附资产 ID、版本和段落定位，候选及关系能回指知识证据。这样新旧资料较多时不会因为较新但无关的文档挤出相关内容。

### 模型配置路由当前实现

模型配置页面提供 `ALL`、`ANALYSIS`、`WIKI`、`FAST` 四种使用场景以及 `OPENAI_COMPAT`、`OLLAMA`、`LOCAL_COMPAT` 三种接入类型。后端 `LlmWikiClient.configForScene` 会按场景选最新启用配置，找不到专属场景时回退 `ALL`。当前调用路径大致如下：

| 场景 | 调用用途 | 是否进入场景路由 |
|---|---|---|
| `ANALYSIS` | 分析任务的整体语义补充、名称补全；分析范围里的对话回答/修正 | 是。`AnalysisJobServiceImpl` 注入的 completion 回调调用 `analysisCompletion`，固定选择 `ANALYSIS` |
| `WIKI` | 原始资产整理成 Wiki 页面 | 是 |
| `FAST` | 非分析范围的普通 Wiki 问答 | 是 |
| `ALL` | 其他通用/兼容调用的默认配置 | 是，作为上述场景未配置时的回退 |

所以，页面上的**场景分配并非纯展示，分析确实会优先使用 `ANALYSIS` 模型**，Wiki 整理和普通问答也会分别优先使用 `WIKI`、`FAST`。同一场景多条启用配置时，SQL 按 ID 倒序只取最新一条。

但“按功能选择模型”目前只到**场景级别**，没有分析内部按阶段配置。例如结构化语义描述和中文名称补全都使用同一个 `ANALYSIS` 场景，没有各自的模型/温度/token 策略或失败回退策略。前端的接入类型虽然能保存和显示，主分析/问答运行期的场景查询没有返回 `provider_type`，`configForScene` 也没有读取或返回它；最终均经同一 `/chat/completions` 请求格式和 Bearer Key 调用。因此不能认为 Ollama、本地兼容、其他 API Key 模式有各自真实运行适配。配置测试同样固定请求 `{baseUrl}/models`，不会按提供商探测，连接测试通过也不足以证明对应生成路径可用。Ollama 如果手动配置了 OpenAI 兼容 `/v1` 接口可能偶然可用，但这不是由 `OLLAMA` 类型实现的原生路由保证。

另外，保存后的多配置目前由模型场景路由读取，但 `ontology_llm_settings` 里的旧单配置读写类仍存在。运行调用与旧配置页/旧配置路径需要分别确认，避免运营人员误以为只改了某个“默认模型”就会覆盖所有场景。建议 UI 对每种配置展示被哪些实际调用点使用，并提供按场景发起真实 completion 的测试；后端先实现明确的 `LlmProvider` 适配器选择和接口兼容测试，再开放提供商类型选项。若短期只支持 OpenAI 兼容接口，应先把 UI 的接入类型收敛为已验证的兼容模式，避免“已保存/测试成功”造成支持多提供商的误解。

后续若确需按分析子功能分配模型，应将路由键从单一 `usage_scene` 扩展为稳定的能力/阶段标识，例如 `analysis.semantic-enrichment`、`analysis.name-completion`、`wiki.ingestion`、`wiki.answer`，并保留场景默认回退。每次分析运行记录实际选中的配置 ID、provider、模型、提示/配置版本和阶段调用结果，不能只在当前草案里保留最终输出。

## 建议的目标层次

```text
接口层
  REST/MCP Controllers：鉴权、参数校验、响应适配
应用层
  Wiki Ingestion / Retrieval / Q&A
  Schema Scan / Analysis Job / Proposal Governance
  Data Query Use Cases
领域层
  Schema Catalog、Ontology Candidate、Evidence、Wiki Chunk、Query Plan
  规则、状态迁移、版本、置信度与冲突处理
适配层
  MyBatis 持久化、业务库 JDBC、LLM Gateway、Embedding/Retrieval Provider、消息/任务执行器
```

这是一种代码边界目标，不要求现在新增独立部署服务。模块间通过稳定 DTO/接口交互，避免 `core` 和 `query` 直接互相依赖实现；把共享能力提到 `common` 前，应确保其为真正稳定、无业务策略的契约，避免公共模块变成新型大杂烩。

## 分阶段实施建议

### P0：先建立可度量的基线

- 对 1000 表基准库记录表/列/关系数、扫描时间、峰值内存、批次失败恢复耗时、模型调用量与 token。
- 建立 Wiki 检索评测集，覆盖中文表述、同义词、简称、原文引用、过期与冲突知识，以及用户/空间范围隔离。
- 指标需设定目标环境和硬件基线后确定，避免未经压测承诺性能数字。

### P1：可控的规模化基础

- 把元数据扫描结果按批次写入结构目录，记录指纹和扫描状态，任务检查点指向已完成批次。

## 规模验收建议

1. **数据库规模**：至少 1000 张表，覆盖跨 schema、宽表、视图、无外键表、同名字段、复杂外键、多数据库方言和大字段注释。验证全量扫描、批次失败重试、任务恢复、取消、增量变化传播和版本回滚。
2. **Wiki 规模**：以预计生产文档数、平均正文长度和 chunk 数的倍数做压测，覆盖新建/更新/删除/停用、重建、并发问答和空间权限过滤。
3. **准确度**：分析候选测实体/属性/关系 Precision、Recall 和证据覆盖；问答测 Recall@K、MRR/nDCG、引用精度和无证据处理；自然语言查询测计划正确率、澄清正确率及 SQL 执行结果。
4. **性能与恢复**：记录扫描/检索/模型/SQL 各阶段 P50/P95 延迟、CPU/堆内存、数据库连接占用、索引构建时间、失败批次恢复时间和成本。
5. **隔离与安全**：验证不同用户、空间、任务、资产和数据源无法通过检索、引用、历史、导出或缓存串读；模型输入遵循当前范围和样例脱敏规则。

只有基准数据、部署规格、通过阈值和测试结果都被记录后，才把“适配 1000 张表”或“支持大规模 Wiki”作为已验证能力对外表述。

本次为源码静态评审，没有连接客户数据库、模型服务或生产环境，也没有运行整套自动化测试。因此，扫描耗时、检索召回质量、并发能力和 1000 表端到端可用性仍需按上述基准实测。代码行数和建议拆分是结构信号，拆分顺序应结合变更频率、测试覆盖及实际故障/协作成本调整。
