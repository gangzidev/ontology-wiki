# 数据查询侧栏与实体关联查询改造计划

> 制定日期：2026-11-24  
> 范围：数据查询左侧“分析”信息重构，以及基于已审核本体关系的实体关联查询。  
> 依据：当前工作区数据查询页面、查询目录/计划/校验/SQL 编译链路和关系推理配置。本文是技术规划与实施顺序，不代表功能已实现。

## 1. 目标与问题

用户应能用业务语言询问“获取 XXX 用户相关的信息”，系统以该用户为中心识别关联业务数据、说明关联含义并提供可继续展开的结果。用户不应先理解数据表、字段名或连接条件。

当前查询页左侧有“历史、目录、分析”三个页签。“目录”将表字段、指标、维度和时间维度放在同一棵树中；“分析”又同时展示表/字段计数、当前查询来源表、表结构、字段、旧抽样画像、关系字段映射和推断证据。关系卡片直接暴露 source/target 字段及推断状态，页面还提示用户自行判断关系证据。它是面向配置审查的技术视图，不适合作为业务查询用户的主要导航。

后端已有关系目录和按关系路径编译 JOIN 的基础，也支持中间表连接。但目前明细计划有一个 `detailObjectId`，其展示字段必须属于这张表；关系路径主要用于把指标、过滤字段等连接起来，并不会自动按关联实体拆分返回用户的全部关联信息。因此，“有关系配置”还不等同于“能按实体获取关联信息”。

改造应形成两个相互配合的能力：左侧帮助用户理解当前配置能查询什么；查询引擎基于已审核关系执行实体中心的关联查询，并在结果中解释来源和关系。

## 2. 产品交互方案

### 2.1 左侧导航

将当前“历史 / 目录 / 分析”调整为：

| 新页签 | 面向用户的内容 | 主要操作 |
|---|---|---|
| 历史 | 当前草案下的历史问题和会话 | 新建、恢复、继续会话 |
| 可查内容 | 业务对象、常见问题、指标和分类；优先显示业务名称和同义词 | 搜索后点击对象或问题以填入输入框 |
| 关系探索 | 以业务对象为起点，显示已确认的“属于、负责、创建、参与”等关系及关联对象 | 选择起点、展开一层关系、将所选关系作为查询意图 |

“可查内容”默认按业务概念组织，例如“用户、订单、部门、项目”，而不是让用户先在“数据表/字段/指标/维度”之间判断。字段和物理表名仅在对象详情或高级信息中查看。统计指标仍可搜索和选择，但应以“订单金额（按订单金额汇总）”等业务标签出现。

“关系探索”用紧凑的对象关系图/列表表达方向和含义，例如“用户 — 创建 → 订单”“用户 — 属于 → 部门”“用户 — 参与 → 项目”。每条关系显示审核状态、关联对象和简要业务说明；映射表、字段、推断方法、置信度、证据等放在“技术详情”折叠区。默认只展示已确认且可执行的关系；待审核关系单独分组，不能被暗示为可查询能力。

当前查询结果上的“来源结构与关系”改为“查询依据”。打开后聚焦本次实际使用的对象和关系路径，按业务名称说明“通过用户账号关联到订单”，并提供“查看技术详情”入口。没有关系参与时明确显示“本次查询只读取……”，不显示空白关系面板。

### 2.2 典型查询流程

1. 用户输入“获取张三相关的信息”。语义目录识别用户对象和可能的姓名字段，先按只读查询查找匹配实体。
2. 若没有匹配实体，说明未找到并允许调整条件；若有多个匹配项，返回可区分的有限候选（例如姓名、账号、部门），让用户选择，不能任取一条。
3. 确认实体后，按问题约束和查询策略发现可执行的关联关系。默认返回该对象的基本信息及一层直接关联概览；不要无上限遍历全图。
4. 关联结果按关系分组展示，例如“基本信息、所属部门、角色、参与项目、负责工单”。每组独立分页/展开，空结果显示“没有匹配记录”。
5. 用户可继续问“展开他的项目”或“查看他负责的未完成工单”；新计划继承已确认的实体标识，并在上下文变化时重新校验配置版本和权限。

关系含义必须保留。用户到部门、用户到其部门内全部员工，不是同一种“用户相关信息”；“创建订单”和“审批订单”也不能合并成无区别的订单列表。默认只走显式、已审核、方向明确的关系；间接路径只在用户表达了目标对象/业务动作或经确认的扩展规则允许时展开。

## 3. 技术方案

### 3.1 查询计划和语义对象

在现有统计计划及单表明细计划之外增加独立的 `ENTITY_RELATION` 查询类型，避免把实体遍历伪装成统计指标或把多实体结果塞入单表明细。

建议计划结构如下，具体 DTO 名称在接口设计阶段定稿：

```json
{
  "queryType": "ENTITY_RELATION",
  "rootObjectId": "user",
  "rootLookup": {
    "propertyId": "user_name",
    "operator": "=",
    "value": "张三"
  },
  "relationIds": ["user_department", "user_roles", "user_projects"],
  "depth": 1,
  "limitPerRelation": 100
}
```

计划校验器负责验证根对象、查找字段、关系方向、字段映射、关系状态、深度和结果限制。模型只负责从问句解析候选对象/关系/过滤条件；所有 ID 必须来自当前已审核配置。实体匹配无结果或有歧义时返回结构化候选/澄清，不进入关联展开。

关系需有一致的可执行语义：稳定 ID、源/目标对象、方向及人类可读关系名、基数、连接列或中间表映射、审核状态、证据和配置版本。现有字段（如 `reviewRequired`、`inferenceMethod`、`cardinality`、`sourceColumn`、`targetColumn`、`viaTable`）可作为迁移基础，但要明确区分“候选推断”“已确认可执行”“不可执行/映射不完整”。不要仅根据置信度自动开放执行。

### 3.2 执行和结果编排

第一期采用受控、分组的只读查询：先按根查找条件解析唯一实体，再以根实体 ID 为锚点，对每条获准关系独立编译和执行有限结果集，最后按关系 ID 聚合为实体关联响应。独立查询可避免多条一对多关系同时 JOIN 时出现笛卡尔放大、重复行和统计口径污染；同一条关系内部仍可由现有 SQL 编译器处理一对一、一对多和已映射多对多路径。

执行器应复用现有数据源只读连接、参数化查询、超时和行数上限。为控制额外负载，加入全局关系数上限、单关系行数上限、总行数/响应体积上限和请求超时；关联结果支持按关系分页，下一页仍绑定同一个根实体、关系和配置哈希。按每次业务请求复用连接，明确是否使用事务快照；在跨查询无法保证同一快照时，返回时间信息或在 UI 中避免暗示严格一致性。

结果采用按组返回，而不是把多表结果摊平成一张宽表：

```json
{
  "root": {"objectId": "user", "entityId": "...", "label": "张三"},
  "relations": [
    {
      "relationId": "user_projects",
      "label": "参与项目",
      "targetObjectId": "project",
      "rows": [],
      "hasMore": false,
      "evidence": {"path": ["user_projects"], "configHash": "..."}
    }
  ]
}
```

执行失败按关系组返回可理解的失败状态，同时整体响应标明部分成功；不能把失败误显示为“没有关联数据”。历史记录保存查询意图、根实体引用、关系分组元数据和安全策略允许的结果快照；应用与隐私策略决定是否保存明细值，避免无条件扩大现有完整结果快照的暴露面。

### 3.3 关系选择和路径规则

- 默认展开一层直接关系，且只执行审核通过、映射完整、查询白名单允许的关系。
- 关系方向按关系定义保留。反向展示必须是显式且语义正确的反向关系，不能只因 JOIN 可逆就自动替换业务含义。
- 多条同等路径、路径含待审核关系、缺少连接映射、跨数据源或连接对象未纳入查询授权时，返回澄清/不可用原因，不猜测连接。
- 中间表必须满足现有的完整端点映射要求；关联表自身如需作为业务结果展示，应另定义对象和有意义的关系，不能泄露为“技术表”。
- 间接展开必须声明最大深度、允许关系集合和结果预算；禁止无约束图遍历及循环访问。
- 默认不对未请求的隐私敏感属性做广泛投影。根对象查找字段、关联对象字段和行级范围应遵守数据源权限及应用授权。

### 3.4 API 与前端状态

首选沿用现有 `/ontology/data-query/plan` 与 `/ask` 入口，根据计划类型路由到不同校验和执行器，避免产生多套自然语言解析入口。若首期联调需要单独执行端点，应使用明确的实体查询 DTO，并沿用现有认证、草案权限、历史和配置哈希校验。目录返回增加面向业务展示所需的关系名称、审核/可执行状态、方向标签和技术详情字段，不将连接 SQL 暴露给模型或普通用户。

前端区分以下状态：实体查找中、需要选择实体、没有实体、已找到实体、各关系组加载/成功/为空/失败、还有更多数据、配置已变化。查询依据面板只展示实际执行的关系路径；关系探索中的点击只构造查询意图，不直接执行未确认的关系。

## 4. 实施阶段与交付

### 阶段 0：业务关系和边界基线

整理真实业务对象与用户中心用例，选取“用户—部门/角色/项目/工单”等代表路径，明确每条关系名称、方向、基数、审核规则、展示字段、权限和可扩展深度。盘点关系配置真实形态及目标数据库限制，建立自然语言到计划的标注问句集。

**交付**：关系语义清单、实体查询 API/结果契约、首期白名单、基线问句与数据权限验收用例。  
**验收**：每条首期关系都有业务解释、唯一可执行映射和责任人；歧义及无映射用例有确定的澄清/拒绝结果。

### 阶段 1：左侧信息架构和查询依据

重组侧栏为“历史、可查内容、关系探索”；以业务对象优先，技术表/字段/画像移入对象详情或技术详情。将“来源结构与关系”改为本次“查询依据”，并清楚区分关系已确认、待审核、不可执行和本次未使用。保留查询输入框、现有目录操作和移动端侧栏行为。

**涉及**：`frontend/src/views/ontology/data-query/index.vue`、必要的目录展示 DTO 与页面组件。  
**验收**：新用户能从左侧回答“可查哪些业务内容、对象间如何关联、当前结果用了哪些关系”；不需解释 source/target 字段即可看懂关系；高级用户仍可查到字段映射和证据；移动端和桌面无内容溢出。

### 阶段 2：关系可执行性和实体解析

统一关系状态和目录输出；在服务层实现实体查找计划、查找字段白名单、唯一性检查和歧义候选；补充候选限制与对象/属性授权校验。先完成仅根实体查找的端到端流程，不自动展开关联结果。

**验收**：唯一、零匹配、多匹配、别名、无权限和不可信筛选分别有测试；模型不能指定目录外字段或自行构造关系 ID；待审/缺少映射关系不能进入执行。

### 阶段 3：按关系分组执行与结果展示

实现 `ENTITY_RELATION` 计划验证、关系预算、逐关系参数化查询、分页、部分失败状态和证据响应；前端以根实体摘要和关系分组展示，并支持按组展开及继续追问。为既有统计/明细计划保持兼容，显式路由新查询类型。

**验收**：一对一、一对多、多对多均按正确映射取数；并行存在的多条一对多关系不造成行数相乘；翻页不改变根实体；失败不被表示为空；历史恢复和配置更新哈希校验正确。

### 阶段 4：间接关系、质量评测和规模优化

依据首期使用数据开放少量经过确认的二跳关系和关系过滤追问。增加自然语言计划评测、关系路径精确率、实体消歧正确率、结果完整性、响应延迟和 SQL 执行量指标。根据真实负载再决定连接池、批量查询或关系结果缓存策略。

**验收**：深度及预算限制有效；循环、歧义路径、越权和多租户边界均被拒绝；核心标注集通过约定阈值，且 P95 延迟、单问 SQL 数和返回体积在目标数据源可接受范围内。

## 5. 测试矩阵

| 层次 | 核心场景 |
|---|---|
| 关系目录/语义 | 方向、标签、审核状态和映射完整性；候选关系不得作为确认关系 |
| 实体解析 | 唯一命中、零命中、同名歧义、别名、特殊字符参数绑定、敏感字段授权 |
| 关系执行 | 单表直连、一对多、多对多中间表、反向关系、缺映射、多条等长路径 |
| 组合语义 | 两条独立一对多关系不会产生乘积重复；“创建/审批/负责”等关系含义不混淆 |
| 安全与容量 | 越权对象/字段、待审核关系、深度限制、每组分页、总行数、超时、超大结果 |
| 失败与历史 | 单组失败和部分成功、配置哈希变化、历史恢复、空结果与失败状态区分 |
| 前端交互 | 业务词汇可读、技术详情折叠、当前查询依据准确、桌面/移动端布局和键盘可达性 |

## 6. 非目标与风险

首期不把关系图当作无限制图数据库，不遍历所有可达表，不根据名称相似或单纯连通性自动开放关系，也不把多类关联记录强行合并为一张表。系统继续使用当前业务数据库及受控 JDBC 查询，不要求新增图数据库。

最主要的产品风险是“相关”的范围没有业务共识；必须通过首期关系白名单和澄清交互控制。主要工程风险是不同数据源的分页、快照和 SQL 方言差异，以及多关系查询的额外数据库负载。安全风险是通过实体关联扩大原本单表查询的可见字段/记录范围，需把授权检查落实到每个关系组和每个目标对象，而不是只检查根对象。

## 7. 推荐实施顺序

先完成关系语义与权限基线，再交付左侧可理解的关系探索和本次查询依据；随后实现实体唯一性解析、按关系分组查询及分页，最后才逐步开放二跳路径。每阶段都以真实业务关系和可复现用例验收，避免只用能生成 SQL 作为完成标准。
