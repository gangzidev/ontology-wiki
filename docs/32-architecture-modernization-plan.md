# 架构与分析能力改造计划

> 制定日期：2026-11-23  
> 依据：`docs/31-architecture-review-and-scale-recommendations.md` 的源码评审结论。  
> 目标：让分析范围可控、模型路由与配置页面一致、Wiki 和数据库结构增长后仍可检索与分析，并降低核心代码的修改风险。  
> 实施原则：保留模块化单体和现有用户工作流，按阶段交付可验证能力；先修正页面与运行行为的一致性，再建设规模化数据链路，最后依据实际负载决定是否需要拆分进程。

## 目标结果

完成改造后应满足以下条件：

1. 用户可以分别定义业务分析目标和数据库对象范围，并能看到本次分析实际覆盖的 Schema、表及知识空间。
2. 每项页面配置都有可验证的后端行为。分析阶段选择会真实控制执行，样例数据设置会进入分析任务并经过脱敏。
3. 模型配置明确区分使用场景和提供商能力。分析、Wiki 整理、问答等调用可追踪实际模型及配置来源，连接测试能验证实际生成路径。
4. Wiki 页面关系被持久化并可增量更新，提供结构化关系查询和可供 LLM 导航的 Markdown 关系索引。Wiki 和数据库元数据按增量维护并分批处理，模型上下文仅包含当前任务需要的对象、知识证据和关系摘要。
5. 分析结果保留结构、知识、模型及人工修订证据，可检查、重放和比较。
6. 核心服务和前端页面按业务职责拆分，API 和已有草案兼容性有回归保障。

## 实施阶段

### 阶段 0：确认范围语义并建立基线

**目标**：把产品术语、当前行为和规模验收口径固定下来，避免实现过程中把“业务目标”误作“数据库过滤条件”。

**改造内容**：

- 将分析输入定义为业务目标、数据源、Schema/表白名单、排除表、知识空间、样例策略、阶段选择和可选 SQL 示例。
- 明确未指定表范围时的默认行为。建议保留“全部可见表”的兼容选项，并在执行前显示预计表数和范围摘要。
- 明确全量、增量、恢复、表删除、权限不可见表和结构变化的处理规则。
- 确认分析阶段的稳定 ID、阶段依赖、跳过阶段时结果如何补齐，以及已有草案的兼容策略。
- 确认模型场景、提供商类型、API 兼容协议和当前正式支持的组合。
- 建立 1000 表样例库与 Wiki 检索评测集，记录运行环境、数据规模和基线指标。

**交付物**：分析任务输入契约、阶段依赖说明、模型路由矩阵、基准数据集及基线报告。

**验收标准**：每个表单字段都能映射到明确的后端字段和业务行为；默认范围、阶段跳过及模型回退均有确定规则；基线可重复运行。

### 阶段 1：修正分析范围、阶段和样例配置

**目标**：让用户选择的分析范围和页面描述与实际扫描、生成行为一致。

**改造内容**：

- 在分析任务中增加 Schema/表范围选择、搜索、分页和排除系统表能力；保存范围快照，供任务恢复与版本比较使用。
- 将“分析范围”拆分为“业务目标说明”和“数据库对象范围”。业务目标只作为语义上下文，不承担表过滤职责。
- 在分析启动前展示将扫描的 Schema、表数、排除项、知识空间及样例策略；全量范围过大时允许用户缩小范围后再启动。
- 为分析任务增加样例策略配置，支持关闭样例、选择表和设置受限条数。只对选择的表读取样例，复用脱敏逻辑并补充字段级允许/禁止规则。
- 实现 `stages` 的执行控制和阶段依赖校验。被跳过阶段应有明确状态和原因，不得把“未执行”伪装成已完成结果。若暂不支持选择，则移除该请求参数和结果字段中的误导信息。
- 对 SQL 示例使用受支持方言的解析器或限制为简单示例格式，并在页面说明只提取哪些信息；继续确保不执行用户输入的 SQL。
- 将任务请求、范围快照、样例策略和阶段选择纳入恢复签名。恢复时输入范围不一致应拒绝继续并说明原因。

**涉及模块**：分析任务页面/API、`AnalysisJobServiceImpl`、`DataSourceScanner`、`OntologyGenerationEngine`、任务检查点与草案元数据。

**验收标准**：

- 首次全量分析只读取范围快照中的对象；范围外对象不会进入结构快照、候选或模型提示。
- 增量更新只重扫选择的变化对象，并能检测未知表、跨 Schema 同名表及已删除表。
- 每个分析阶段的执行状态与用户选择一致，阶段依赖错误能在任务启动前反馈。
- 样例关闭时没有业务数据查询；样例开启时只查询授权选择的表并按规则脱敏。
- 任务恢复会复用同一输入快照，范围或策略改变时明确要求重新分析。

### 阶段 2：补齐模型提供商和场景路由

**目标**：使模型配置页可见的接入类型、场景分配和测试行为与分析/问答实际调用一致。

**改造内容**：

- 定义统一的模型请求/响应接口，并按提供商实现适配器。至少区分 OpenAI 兼容服务和 Ollama 原生接口；`LOCAL_COMPAT` 要明确是否只是 OpenAI 兼容服务的部署标签，避免和协议类型混为一谈。
- 场景配置读取必须返回 provider、模型、配置 ID、地址和认证方式。运行时根据 provider 选择请求路径、认证头、请求体与响应解析。
- 按实际支持协议实现配置测试。测试应调用与生成一致的端点和请求，不能仅以 `/models` 可访问判断生成可用。
- 保留 `ALL` 默认配置回退，并明确同一场景多条启用配置按最新配置生效。配置缺失、密钥错误、provider 不匹配应反馈具体场景和配置状态。
- 将 `ANALYSIS` 内部路由细化为可选能力键，例如语义补充、名称补全；设置阶段级默认配置时仍能回退到 `ANALYSIS`、再到 `ALL`。
- Wiki 整理、Wiki 问答、普通快速问答、分析问答和分析生成都通过同一模型网关，避免存在绕过路由的旧调用路径。
- 每次调用记录脱敏后的配置 ID、provider、模型、场景/能力键、耗时、token 用量（服务可提供时）、重试和失败原因。密钥不得写入日志。
- 检查旧单配置入口的读写路径，明确其迁移策略，并确保旧配置不会覆盖多场景运行路由。

**涉及模块**：模型配置页面/API、`LlmWikiClient`、`LlmConfigService`、模型配置 Mapper、分析 completion 回调和模型调用日志。

**验收标准**：

- 每种对外开放的 provider 都通过真实协议的连通测试和 completion 测试。
- ANALYSIS/WIKI/FAST 调用使用对应最新启用配置，缺少专属配置时按预期回退。
- 阶段级配置生效且可追踪；旧调用均经过统一路由。
- 测试页显示实际选中的 provider、模型和测试结果，不把错误端点返回当作连接成功。
- 并发保存、禁用和修改配置时，新任务读取到一致配置；运行中的任务是否固定启动时配置需明确并通过测试。

### 阶段 3：Wiki 资产索引与相关证据检索

**目标**：从固定数量的最新文档读取和内存关键词排序，升级为范围安全、可增量、可评测的检索流程，并把页面关系从请求时临时解析改为可持久化、可重建的关系索引。

**改造内容**：

- 设计 Wiki chunk 数据模型，记录空间、资产、版本、段落、标题、来源、内容校验和索引状态。
- 资产新增、编辑、删除、停用、空间变更和权限变更时，只更新受影响资产的索引；提供可恢复的后台全量重建任务。
- 先按用户、空间、资产/任务范围和状态过滤，再进行关键词召回。对中文术语、字段名、简称和同义词采用可配置的字段权重。
- 以关键词召回作为首阶段能力，并通过检索接口预留 Embedding Provider；只有基准集证明语义召回能提升效果后，再接入向量存储和融合排序。
- 查询返回 Top-K 证据块，按 token 预算组装上下文；保留资产 ID、段落位置、版本和得分，问答引用回链到原文。
- 分析任务使用相同的证据召回能力，查询条件包括任务描述、表名/字段名/注释和已识别术语。移除按更新时间直接取前 100 条的相关性依赖。
- 建立持久化 Wiki 页面关系目录，记录源资产、目标资产或未解析目标、关系类型、目标名称、来源位置、源页面版本和更新时间。关系类型至少区分显式 Wiki 链接、Markdown 链接、原始资料来源和分析引用。
- 将现有图谱接口改为读取关系目录，避免每次请求加载最多 2000 个节点并重新扫描正文正则。支持按知识空间分页查询节点、边、入链和出链。
- 页面创建、编辑、删除、停用、重命名和空间迁移时增量重建该页面的出链，并维护受影响目标的反向链接。目标尚不存在时保留未解析边，目标后来创建后能够重新解析。
- 生成可重建的 Markdown 关系索引，按知识空间和页面分组列出页面链接、反向链接、来源资料及分析依据，保留标准 Markdown 链接或稳定资产 ID。此索引用于 LLM 导航和人工浏览，避免将所有关系塞进单一无限增长文件。
- Markdown 关系索引带索引版本和生成时间，支持按空间或页面重建；关系存储是权威数据，Markdown 是可重建投影。索引生成失败可以重试，不影响页面内容保存和结构化关系读取。
- 全局 Markdown 标题/摘要目录继续作为人工导航入口，不再承担高召回检索职责；避免每次页面变化都重写超大单页目录。

**涉及模块**：Wiki 摄取和页面服务、检索 Mapper/服务、页面关系提取与存储、Markdown 索引投影任务、问答上下文组装、分析知识加载和前端资产关联图。

**验收标准**：

- 权限和知识空间过滤在召回前执行，搜索、引用和缓存均不能跨空间串读。
- 更新单个资产只重建该资产相关块；失败可重试，全量重建可中断恢复。
- 对固定评测集报告 Recall@K、MRR/nDCG、引用准确率、无证据处理率和 P95 检索延迟。
- 资产数增长时，问答提示词长度受预算约束，不随资产总数线性增长。
- 页面关系目录能按来源、目标、关系类型和空间查询；前端图谱与 LLM 导航索引读取相同的关系事实。
- 页面新增、编辑、重命名、移动、删除和停用后，出链、入链、未解析链接及 Markdown 投影能正确更新；任务可重试且可从全量重建恢复。
- Markdown 关系索引按空间分片生成，链接可回到稳定页面/资产标识；缺失目标可识别并支持后续重新解析。
- 旧资产、无索引资产和索引重建期间有明确降级行为及可观测状态。

### 阶段 4：数据库元数据分批扫描与增量分析

**目标**：使 1000 张及更多表的结构扫描、生成、恢复和版本治理可控。

**改造内容**：

- 按数据库类型实现稳定排序、Schema 游标/分页的元数据读取适配。对 JDBC 驱动不支持分页的情况，分批拉取系统目录或分段处理，并避免将完整对象图长期驻留内存。
- 建立表、列、主外键、索引元数据目录及结构指纹。记录扫描批次、游标、状态、错误、耗时和指纹。
- 将扫描任务、确定性候选生成和 LLM 语义补充分开保存检查点，支持批次独立重试和失败隔离。
- 基于外键建关系图；对无外键的推断关系保存方法、证据和置信度，进入待审核候选，不自动当作事实。
- 按 Schema、业务域和关系连通区域生成分析单元；每次模型调用只携带局部表、相关邻居和召回到的 Wiki 证据，设置表数、字段数、token、并发、超时和重试预算。
- 表结构指纹未变化时复用已审核映射。结构变化时只重算受影响表及关系邻域，并同步处理删除表、字段改名和映射冲突。
- 版本记录关联扫描快照、范围配置、Wiki 索引版本、模型路由和人工修正，保证可比较和可追溯。

**涉及模块**：`DataSourceScanner`、元数据目录与 Mapper、分析任务执行器、`OntologyGenerationEngine`、检查点存储和草案版本。

**验收标准**：

- 1000 表基准库完成全量扫描、候选生成、恢复、取消、增量更新和版本回滚。
- 单批失败不会丢失已完成批次，重试不会重复生成或覆盖人工修正。
- 指纹不变时不重复执行扫描后的高成本分析；变化影响可追溯到具体表和关系。
- 记录扫描/生成/模型阶段的 P50/P95 耗时、峰值内存、失败率和 token 成本，并与阶段 0 基线比较。
- 多数据库方言、跨 Schema、宽表、视图、无外键、同名字段及大注释场景通过测试。

### 阶段 5：核心类与页面按职责拆分

**目标**：降低高变更区域的耦合，确保新检索和路由边界稳定后再迁移业务调用。

**改造内容**：

- 将 `LlmWikiClient` 逐步拆为模型网关、模型配置、Wiki 问答、Wiki 整理、分析对话/知识沉淀等应用服务。迁移期间保留兼容门面，按一类调用一次迁移。
- 将 `OntologyController` 拆为资源/资产、分析任务、Wiki 对话、模型配置和草案/导入导出控制器。控制器只调用应用服务，不直接拼装复杂图谱或持有多个持久化 Mapper。
- 按持久化职责拆分 `WikiAssetMapper`，并对每组 SQL 保留参数绑定、分页、权限和结果兼容检查。
- 拆分 chat 页面中的历史、消息与引用、分析变更确认等组件；拆分 data-query 中计划、结果、下钻、比较、图表和历史组件。
- 维持现有 API 路径和草案 JSON 兼容；如必须调整格式，提供版本字段、读取兼容和显式迁移。

**验收标准**：

- 拆分前后关键用例输出一致，分析候选、引用、模型路由、草案版本和查询行为通过回归。
- 新 Controller 不直接访问 Mapper；页面子组件有单一输入/输出契约，不复制请求和状态规则。
- 无无关格式化或批量重命名导致的 diff 噪音。

### 阶段 6：运行观测与部署形态复核

**目标**：用运行数据判断是否需要独立任务 Worker、检索服务或微服务。

**改造内容**：

- 建立任务阶段耗时、队列等待、租约过期、取消时延、模型失败、检索延迟、数据库连接和索引积压等指标。
- 提供任务批次状态、模型调用追踪、索引版本和失败重试记录的管理视图。
- 按真实并发、吞吐、故障隔离、资源竞争和部署弹性评估是否将异步分析 Worker 或检索索引进程独立部署。

**验收标准**：

- 可从任务 ID 追踪输入范围、扫描批次、Wiki 证据、模型调用和最终候选版本。
- 运行指标能区分数据库、模型、检索和应用自身瓶颈。
- 部署拆分由测量数据和隔离需求驱动，且有服务边界、重试和数据一致性方案。

## 建议优先级与依赖

| 优先级 | 阶段 | 原因 |
|---|---|---|
| P0 | 阶段 0 基线与契约 | 为后续功能设定一致输入和可比较验收条件 |
| P1 | 阶段 1 范围/阶段/样例 | 直接影响分析结果范围、成本和用户对页面能力的理解 |
| P1 | 阶段 2 提供商路由 | 当前配置页存在选择项与运行行为不一致的问题 |
| P1 | 阶段 3 Wiki 检索与关系索引 | 知识增长会影响证据召回；页面关系需持久化供图谱、反向链接和 LLM 导航共同使用 |
| P2 | 阶段 4 1000 表扫描与分析 | 依赖范围契约、批次模型和检索证据能力 |
| P2 | 阶段 5 类与页面拆分 | 在目标边界稳定后迁移，减少重复返工 |
| P3 | 阶段 6 部署形态评估 | 需要前述运行数据后再做架构决策 |

阶段 1、2、3 可以在基线完成后并行细化，但共享模型调用接口、Wiki 证据 DTO 和分析请求契约应先定稿。阶段 4 应建立在元数据范围和证据接口稳定之后。阶段 5 每次只迁移一个业务用例，避免与行为改造同时大规模重构。

## 交付与变更管理

- 每个阶段拆成可单独验收的小批次，先完成数据契约和兼容策略，再进行代码迁移。
- 新增元数据、索引或运行日志表使用增量迁移脚本，禁止用初始化 SQL 覆盖已有业务库。
- 变更前后记录 API 字段、配置场景、草案 JSON 和数据库表结构兼容情况。
- 对安全范围、敏感样例、模型输入、历史记录和 Wiki 引用执行跨用户/空间隔离检查。
- 每次交付报告源码改动、迁移脚本、自动化测试、基准结果和仍未验证的生产假设。

## 当前未纳入本计划的事项

本计划暂不承诺特定硬件下的扫描时间、问答延迟、模型成本或准确率数值。阈值应在阶段 0 固定部署规格和代表性数据后设定。本计划也不要求立即拆分微服务；若阶段 6 证明单体 Worker 已成为吞吐或故障隔离瓶颈，再提出独立部署方案。
